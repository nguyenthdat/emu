# Phase 0 Research: Android Research Backends & Security Tooling Integration

## 1. Baseline System Context & Repository Seams

### Current Toolchain, Manifests & Dependencies

- **Toolchain Pin**: `.tool-versions` defines `rust 1.88.0` and `bun 1.2.17`. `Cargo.toml` declares `edition = "2024"`. Note: `Cargo.toml` contains no explicit `rust-version` field; Rust 1.88.0 is the repository pin rather than a verified whole-dependency MSRV.
- **Locked Dependencies (`Cargo.lock`)**: `tokio 1.53.1` (features: full), `clap 4.6.7` (features: derive, env), `ratatui 0.30.2`, `crossterm 0.29.0`, `serde 1.0.229`, `serde_json 1.0.151`, `dirs 7.0.0`, `anyhow 1.0.104`, `thiserror 2.0.20`, `nix 0.29.0`, `libc 0.2.189`. Locked transitive crates available for promotion: `sha2 0.10.9`, `uuid 1.26.1`, `getrandom 0.3.4`/`0.4.3`.
- **Existing Architectural Seams**:
  - _CLI / TUI Entrypoint (`src/main.rs:42-156`)_: Flags (`--debug`, `--log-level`, `--check`) run through `main.rs`. `--check` bypasses raw terminal mode but currently invokes `App::new().await`, which unconditionally triggers background loading tasks (`start_background_cache_loading`, `start_background_device_loading`). Unattended CLI automation requires headless command paths bypassing `App` construction entirely.
  - _Device Dispatch & Traits (`src/app/mod.rs:63-134`, `src/managers/common.rs:31-131`)_: `DeviceManager` uses an associated type `type Device;` with RPITIT; `UnifiedDeviceManager` provides dynamic object-safe dispatch (`Box<dyn Device>`). `App` directly embeds concrete `AndroidManager` and `Option<IosManager>`. `IosManager` and `IosDevice` (keyed by UDID) must remain completely untouched.
  - _Command Execution (`src/utils/command_executor.rs:15-37`, `src/utils/command.rs:84-195`)_: `CommandExecutor` provides `run -> String`, `spawn -> u32` (drops `tokio::process::Child` handle immediately), `run_with_retry`, and `run_ignoring_errors`. Flaws: drops child process handles preventing monitoring or cancellation, lacks per-call environment variables (`env`) and working directories (`cwd`), flattens exit codes into untyped errors, and performs automatic retries that violate invariants on mutating operations.
  - _Persistence & Identity (`src/models/device.rs:14-26/120-140`, `src/utils/cache.rs`)_: Android device identity assumes the AVD name (`&self.name`) is globally unique, colliding across backends. Existing file persistence (`api_level_cache.json`) is a lossy volatile cache using direct `std::fs::write` without locking or atomic swap, not an authoritative durable store.

## 2. Core Architectural & Persistence Decisions

### Decision D-01: Headless Command Routing & Single-Binary Composition

- **Decision**: Retain a single binary. Keep the interactive TUI when invoked without subcommands. Retain `--check` as a non-interactive local check. Route automated operations through headless subcommands (e.g. `device`, `profile`, `run`, `batch`) that instantiate concrete backend managers directly and bypass `App::new()`. Keep `CuttlefishManager` as a concrete manager implementing `DeviceManager` within a cohesive `src/research` service without introducing a dynamic plugin framework or external daemon.
- **Rationale**: `App::new()` in `src/app/mod.rs` unconditionally spawns background tasks that poll devices and mutate shared UI state. Headless CLI execution must run deterministically with predictable exit codes. Embedding concrete managers under `DeviceManager` maintains architectural consistency with `AndroidManager` and `IosManager` while avoiding plugin ABI instability.
- **Alternatives Considered**:
  - _Extracting a separate CLI binary (`emu-cli`)_: Rejected. Increases packaging complexity and duplicates dependency compilation.
  - _Dynamic runtime plugin system (`.so`/`.dylib`)_: Rejected. Unnecessary ABI churn, security surface, and cross-platform complexity for two known Android backends.

### Decision D-02: Backend-Qualified Research Identity & Non-Regression

- **Decision**: Model `ResearchDevice` with a stable, qualified identifier format `<backend>:<opaque>` (e.g. `cuttlefish:cf-x86-01`, `emulator:avd-arm64-sec`). The qualified ID is distinct from the human-readable display name, AVD system name, Cuttlefish instance slot (`cvd-<N>`), display port, and ADB transport serial (`127.0.0.1:6520` or `emulator-5554`). Existing standard Android (`avd:<name>`) and iOS devices (`<udid>`) remain fully backward-compatible.
- **Rationale**: Multiple virtual instances across different backends often share user-visible names. Decoupling the unique internal research identity from ephemeral runtime ports and native names prevents routing collisions and preserves existing iOS UDID assertions.
- **Alternatives Considered**:
  - _Using ADB transport serial as the primary device ID_: Rejected. Ephemeral; changes across daemon reboots, port collisions, or network reconnects.

### Decision D-03: Typed Process Supervision & Safe Command Execution

- **Decision**: Replace untyped process execution with a structured `CommandSpec` (program path, argv, env map, cwd, timeout duration) and `CommandOutput` (exit code, captured stdout/stderr, execution duration, terminal status). Extend `CommandExecutor` with a supervised `spawn_supervised` returning an owned `ProcessHandle` (`wait`, `status`, `terminate`). Strictly prohibit automatic retry (`run_with_retry`) on explicit mutating research operations. Distinguish operation timeout from cancellation, ensure observation Ctrl+C does not trigger task cancel, and confirm cancelled operations return a non-zero exit code.
- **Rationale**: Dropping child handles in `CommandRunner::spawn` risks orphaned processes and zombie PIDs. Mutating operations (storage powerwash, kernel flashing, module injection) partially applied during a failed attempt will corrupt guest filesystems if automatically retried.
- **Alternatives Considered**:
  - _Retaining current `CommandRunner` and tracking PIDs externally_: Rejected. Raw OS PIDs are subject to PID recycling and cannot confirm child process tree exit or stream status.

### Decision D-04: Filesystem Persistence, Locking & Dependency Promotion

- **Decision**: Store all research registries, profiles, artifacts, operations, and execution locks under `dirs::data_local_dir()/emu/research` (`https://docs.rs/dirs/7.0.0/dirs/fn.data_local_dir.html`). A missing data directory produces a contextual application error (no silent fallbacks or unwraps). State files use atomic staged writes (`.tmp` write + flush + `std::fs::rename`; `https://doc.rust-lang.org/std/fs/fn.rename.html`). Propose adding `fs4 = "1.1.0"` with `default-features = false, features = ["sync"]` (`https://docs.rs/fs4/1.1.0/fs4/trait.FileExt.html`, `https://github.com/al8n/fs4/blob/main/Cargo.toml`; MSRV 1.75; MIT/Apache license) for cross-process advisory locking via dedicated, unlinked lock files. Reject `std::fs::File::try_lock` because it stabilizes in Rust 1.89 (`https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock`), which conflicts with the repository's Rust 1.88 pin. Promote transitive crates already in `Cargo.lock` by declaring explicit manifest dependencies: `sha2 = "0.10.9"` (for streaming SHA-256 artifact validation) and `uuid = { version = "1.26.1", features = ["v4"] }` (for opaque ID generation). Unix session detachment will use existing `nix = "0.29.0"` behind `CommandExecutor`; Windows creation flags are owned within executor adapters without generic worker survival guarantees. Implementation gate: Adding these declarations requires a Rust 1.88 compilation verification, platform lock/detach smoke check, and supply-chain review.
- **Rationale**: Staged atomic rename prevents partial writes on crash. Dedicated, stable lock files prevent locking race conditions associated with deleting active lock nodes. `fs4` preserves Rust 1.88 toolchain compatibility while providing standard advisory file locks.
- **Alternatives Considered**:
  - _Embedded SQL engine (SQLite / `rusqlite`)_: Rejected. Introduces C-FFI toolchain overhead, binary blob lock contention, and schema migration weight for low-cardinality research records.
  - _`std::fs::File::try_lock`_: Rejected. Requires Rust 1.89+, which violates the active repository pin (`rust 1.88.0`).

### Decision D-05: Same-Binary Worker Process & Operation Reconciler

- **Decision**: Implement long-running asynchronous execution via a private, finite CLI worker invocation: `emu __worker --operation-id <ID>`. The worker is a single-purpose child process, not a public CLI or background daemon. Before spawning the worker, the coordinator writes an immutable operation request to disk. The worker holds an exclusive operation lock to prevent duplicate execution, acquires a target device lock before mutation, and acts as the sole writer of operation status, events, and checkpoints. The reconciler holds both operation and device locks, inspects runtime guest state rather than relying solely on PID liveness, and never marks an operation stopped merely because a lock was released. Intent is logged prior to each mutation; a crash following intent marks state as `unknown` and quarantines partial artifacts without automated replay. Bounded ring buffers separate typed telemetry events from raw stderr.
- **Rationale**: Long-running kernel flashing and guest boot flows must survive TUI exit without leaking uncontrolled threads or corrupting state files across multiple CLI processes.
- **Alternatives Considered**:
  - _Background daemon service (systemd/launchd daemon)_: Rejected. Heavy operational footprint and external installation requirements for a local CLI harness.

### Backend Virtualization Integration Rules

1. **Tooling Invocations**:
   - _Android Emulator_: Target the SDK low-level command family (`emulator`, `avdmanager`, `adb`; `https://developer.android.com/studio/run/emulator-commandline`). Reject wholesale migration to the new `android emulator` (Android CLI; `https://developer.android.com/tools/agents/android-cli`) because it lacks kernel/image injection flags and is disabled on Windows. Deprecation of legacy CLI tools is noted; runtime capability probing confirms availability.
   - _Cuttlefish_: Manage instances using dedicated isolated runtime roots (`HOME=<isolated_dir>`). Strictly separate client-server `cvd` commands from host-package binaries (`launch_cvd`, `stop_cvd`, `status`, `powerwash_cvd`). Use explicit flags (`--num_instances=1`, `--base_instance_num=<N>`). Refuse imported multi-instance groups to eliminate group-spill risks.
2. **Cuttlefish Group Stop Invariant**: Primary inspection of AOSP Cuttlefish source (`host/commands/stop/main.cc:212-225`; `https://github.com/google/android-cuttlefish/blob/main/base/cvd/cuttlefish/host/commands/stop/main.cc`) reveals that `stop_cvd` forbids stopping the first instance (`base_instance_num`, which may be arbitrary, not always 1) while other group instances remain active, and triggers a fallback `SIGKILL` across candidate process groups via `lsof`. Dedicated 1-instance groups per runtime root prevent cascading kills.
3. **Kernel & Overlay Coupling**: Primary AOSP documentation (`https://source.android.com/docs/devices/cuttlefish/restart`, `https://source.android.com/docs/devices/cuttlefish/kernel-dev`) confirms that custom kernels require Kleaf virtual-device artifacts (`bzImage`/`Image`). Modifying `--kernel_path`, `--initramfs_path`, or base images automatically invalidates and discards qcow2 disk overlays. Swapping kernels is a destructive operation requiring explicit user authorization. Stock AVD images use `kernel-ranchu`; standard phone GKI kernels lack virtual hardware drivers and will fail to boot on both platforms. Restoring a baseline may overwrite guest data; this must be explicitly authorized and never claimed to be lossless.

## 4. Baseline Research Toolchain Triad

### Decision D-06: KernelSU Next v3.3.0 Integration Architecture

- **Decision**: Pin **KernelSU Next v3.3.0** (`https://github.com/KernelSU-Next/KernelSU-Next/releases/tag/v3.3.0`, branch `dev`). Prefer built-in kernel builds (`CONFIG_KSU=y`) on `arm64-v8a` virtual instances; treat `x86_64` as experimental with strict panic guards. Disclose the source asset discrepancy: release assets include prebuilt `.ko` modules for kernel families 5.10 through 6.12, whereas `README.md` describes 4.4 through 6.6; mandate explicit runtime tuple verification rather than universal compatibility claims. Verify root identity via in-guest supercall ioctl probe (`/proc/self/fd/*` matching `[ksu_driver]` and `KSU_IOCTL_GET_INFO`, UAPI version 2 per `uapi/supercall.h`) and `ksud debug info` (`userspace/ksud/src/cli.rs`). Reject generic `adb root` or UID 0 as proof of KernelSU Next activation.
- **Disabling vs Removal Protocols**:
  - _Disabling_: Restore the verified baseline kernel artifact to the device boot partition while preserving manager components (`com.rifsxd.ksunext`) and `/data/adb/ksu` configurations. Upon reboot, verify the driver character node is absent; transition observed status to `inactive`.
  - _Removal_: Restore the baseline kernel artifact, uninstall the manager APK, and purge `/data/adb/ksu` and `/data/adb/ksud`. Invariant: Never purge the shared `/data/adb/modules` directory or touch unrelated tooling.
- **Rationale**: `ksud debug info` directly queries kernel driver UAPI version and flags, preventing false positives from standard userdebug ADB root. Preserving shared directories ensures non-interference with coexisting research tools.
- **Alternatives Considered**:
  - _Generic `su` binary check_: Rejected. Cannot differentiate KernelSU Next from Magisk, SuperSU, or uninstrumented userdebug builds.

### Decision D-07: Frida 17.18.0 Dynamic Instrumentation & Exact Version Pinning

- **Decision**: Pin **Frida 17.18.0** (`https://github.com/frida/frida/releases/tag/17.18.0`, `https://frida.re/docs/android/`). Enforce exact version parity (17.18.0) between the host client and guest daemon (`frida-server-17.18.0-android-{arch}.xz`). Preflight-verify guest ABI via `getprop ro.product.cpu.abi`. Stop operations must target only the managed PID (`kill -TERM <pid>`) or active session handle, strictly avoiding broad `pkill`. Mark operational status as `ready` only after active verification: attach a benign telemetry probe to an authorized sample app using `Process.getModuleByName("libc.so").getExportByName("getpid")` (avoiding `Module.getExportByName`, which was removed in Frida 17) and confirm JSON telemetry receipt.
- **Rationale**: Frida's binary protocol and JSON-RPC transport produce protocol framing errors when client and server versions diverge. Indiscriminate `pkill` kills concurrent user instrumentation sessions. Probing an exported symbol in an authorized app guarantees active hooking capabilities without mutating system services.
- **Alternatives Considered**:
  - _Permitting loose Frida version ranges (e.g. `^17.0.0`)_: Rejected. Transport packet protocol changes between minor and patch revisions introduce intermittent RPC failures.

### Decision D-08: JingMatrix/Vector v2.2 + NeoZygisk v2.4 Xposed Framework Integration

- **Decision**: Select **JingMatrix/Vector v2.2** (`https://github.com/JingMatrix/Vector/releases/tag/v2.2`) running atop **JingMatrix/NeoZygisk v2.4** (`https://github.com/JingMatrix/NeoZygisk/releases/tag/v2.4`) as the supported Xposed-compatible hooking provider. Upstream `LSPosed/LSPosed` is not archived (`archived: false`), but Vector is chosen due to active maintenance for Android 15–17, `libxposed` API 102 hot reload support, and an in-tree native root CLI (`vector-cli`) with `--json` output communicating over `/data/adb/lspd/.cli_sock` (`daemon/src/main/kotlin/org/matrix/vector/daemon/Cli.kt`). NeoZygisk v2.4 provides standalone `ptrace`-based Zygote injection and resolves AVD mount namespace update issues. Enforce module scope assignment via `vector-cli --json scope set <MODULE_PKG> <TARGET_APP_PKG>/0`. Track reboot-dependent states (`pending-reboot`). Transition to `ready` only after active capability verification: a benign test hook modifies behavior exclusively in the designated sample application while a control application confirms baseline behavior. Removal uninstalls Vector modules and purges `/data/adb/lspd` without touching `/data/adb/modules` or other root configurations.
- **Rationale**: Vector provides native, scriptable CLI management with structured JSON output, eliminating fragile GUI automation. NeoZygisk supplies the necessary standalone Zygisk injection absent in KernelSU Next.
- **Alternatives Considered**:
  - _Upstream LSPosed_: Rejected for active research profiles due to lack of recent Android 15+ updates and absence of an official scriptable root CLI.

## 6. Empirical Validation Gates & Methodological Boundary

### Preflight & Lifecycle Validation Gates

1. **Gate G-01 (Host Virtualization Entitlements)**: Linux validates `/dev/kvm` read/write access and user groups (`kvm`, `cvdnetwork`). macOS validates `Hypervisor.Framework` support via `sysctl kern.hv_support`. Windows validates WHPX installation via `emulator -accel-check`. Fail fast on unaccelerated environments.
2. **Gate G-02 (Backend/Host Compatibility)**: Cuttlefish requires host OS `linux`. macOS and Windows report Cuttlefish as `unsupported` and block execution.
3. **Gate G-03 (Cuttlefish Artifact Pairing)**: Verify `cvd-host_package.tar.gz` and `aosp_cf_*` images share identical build IDs before staging to prevent host-guest IPC protocol mismatches.
4. **Gate G-04 (Architecture Alignment & Binary Availability)**: Cross-architecture emulation is out of scope. Linux arm64 Emulator execution requires active runtime verification of native binary availability.
5. **Gate G-05 (Kernel Interface & Target Family)**: User-supplied kernels must target the virtual platform ABI (`virtual_device` for Cuttlefish, Ranchu-compatible for Emulator). Stock phone GKI kernels are rejected preflight.
6. **Gate G-06 (Destructive Overlay Invalidation)**: On Cuttlefish, swapping `--kernel_path`, `--initramfs_path`, or image directories discards qcow2 overlays. Require explicit user authorization identifying the affected instance before proceeding.
7. **Gate G-07 (Port & Instance Group Collision)**: Verify target console and ADB ports are unbound. Enforce single-instance runtime roots for Cuttlefish to prevent `stop_cvd` group-spill failures.
8. **Gate G-08 (Boot Liveness & Operation Timeout)**: Monitor guest boot progression via `sys.boot_completed`. If the operation deadline expires, record a `timed-out` outcome while preserving the actual observed state. Do not automatically kill in-progress instances or falsely declare them inactive.

### Toolchain Empirical Validation Gates

- **Gate T-01 (Guest Boot & Driver Handshake)**: The virtual instance boots within deadline and virtual drivers (`virtio` / `goldfish`) bind without kernel panics.
- **Gate T-02 (KernelSU Next Identity Verification)**: `/data/adb/ksud debug info` successfully queries `[ksu_driver]` and confirms UAPI level 2. Privileged test command logs KernelSU Next identity specifically.
- **Gate T-03 (Frida Server Telemetry Verification)**: Pinned 17.18.0 server launches; host client attaches non-destructive hook (`Process.getModuleByName("libc.so").getExportByName("getpid")`) to an authorized sample app and captures telemetry.
- **Gate T-04 (Vector Scoped Mediation Verification)**: NeoZygisk injects into Zygote; `vector-cli --json status` reports daemon operational; scoped test module modifies behavior exclusively in the designated sample application while a control application retains baseline behavior.
- **Gate T-05 (Joint Concurrency & Mutual Non-Interference)**: KernelSU Next, Frida, and Vector operate concurrently without kernel panics or Zygote crashes.
- **Gate T-06 (Safe Baseline Restoration)**: Upon experimental failure, an authorized recovery operation overwrites guest disks with verified baseline artifacts. Missing baselines safely refuse automated recovery without deleting the device.

### Methodological Boundary

Joint baseline compatibility (KernelSU Next + Frida + Vector) on virtual hardware is an **unobserved candidate configuration** subject to empirical proof. Exact build IDs and SHA-256 digests must be pinned at runtime from user-supplied assets, never fabricated or left as future TODOs. Automated CI relies on deterministic mock executors (`MockCommandExecutor`), isolating real hypervisor and kernel execution to controlled laboratory environments.
